15 / Sul Raspberry

Comandi comprensibili,
con effetti dichiarati.

I comandi di questo capitolo si eseguono in una shell Linux del Raspberry, per esempio via SSH. PowerShell sul PC usa sintassi diversa per alcune operazioni. Il nome dell’utente e il percorso riportati descrivono l’installazione collaudata; adattali per una nuova macchina.

Le basi Linux necessarie per seguire le procedure

La shell interpreta i comandi del terminale. SSH apre una sessione remota: dopo il collegamento, cd, python3 e systemctl si riferiscono al Raspberry, non al PC. Il kernel Linux gestisce processi, memoria, dispositivi e permessi.

  • /home/max/gpio-llm è un percorso assoluto: parte dalla radice /. voice/stt.py è relativo alla directory di lavoro. pwd mostra dove ti trovi; cd cambia directory.
  • Un nome che inizia con punto, come .venv-voice, è normalmente nascosto dalle liste semplici: ls -la lo mostra.
  • stdin, stdout e stderr sono ingresso standard, uscita dei risultati e uscita diagnostica. Il servizio non riceve comandi dalla tastiera come stdin: la CLI è un processo distinto.
  • A | B collega stdout di A allo stdin di B. > redirige a un file e può sovrascriverlo. 2>&1 unisce stderr a stdout; nel worker questo romperebbe il protocollo JSON se applicato senza distinguere i canali.
  • Ctrl+C richiede l’interruzione del processo in primo piano. Nella CLI client chiude quel processo, non il servizio di sistema.
  • Utenti e gruppi regolano l’accesso a dispositivi audio/GPIO e filesystem. Il servizio gira come max, non come root: un errore di permessi richiede verificare l’accesso alla risorsa, non rendere privilegiato tutto il programma per abitudine.

Consultare lo stato senza cambiare nulla

cd /home/max/gpio-llm
systemctl status gpio-llm-ready.service --no-pager
systemctl show gpio-llm-ready.service -p ActiveState -p SubState -p MainPID
journalctl -u gpio-llm-ready.service -b -n 80 --no-pager
systemctl cat gpio-llm-ready.service
ollama list
arecord -l

systemctl status mostra lo stato corrente e log recenti; show restituisce proprietà più adatte a verifiche precise. journalctl -u filtra la unit, -b limita al boot corrente e -n limita le righe. --no-pager evita il visualizzatore interattivo. arecord -l elenca i dispositivi: non apre una seconda registrazione.

Uso quotidiano

Attendi i cinque lampeggi di pronto, pronuncia ASCOLTA da sola, attendi la luce fissa e poi parla. La CLI si apre con il comando seguente e rimane un client del servizio:

cd /home/max/gpio-llm
./target/release/gpio-llm

Il prefisso ./ indica un eseguibile relativo alla directory attuale. Scrivere esci chiude solo il client. Non lanciare --daemon a mano mentre il servizio è attivo: l’esclusività hardware serve proprio a evitare istanze concorrenti.

Compilare e verificare dopo una modifica Rust

cd /home/max/gpio-llm
cargo test --locked
cargo build --release --locked

La compilazione produce un nuovo file sul disco. Non sostituisce il codice che un processo già avviato sta eseguendo. Dopo aver completato i controlli, il riavvio del servizio carica la nuova versione. Un compilato Windows non è il binario ARM64 Linux del Raspberry; per semplicità questa PoC viene compilata sulla scheda.

Verificare una modifica Python

cd /home/max/gpio-llm
.venv-voice/bin/python -m unittest discover -s voice -p 'test_*.py' -v

Python importa stt e autonomous all’avvio del worker. Copiare una modifica .py non fa hot reload nel processo già in memoria. Anche senza modificare il binario Rust occorre un nuovo worker, normalmente ottenuto riavviando il servizio.

Riavviare dopo i controlli

sudo systemctl restart gpio-llm-ready.service
systemctl status gpio-llm-ready.service --no-pager
journalctl -u gpio-llm-ready.service -n 40 --no-pager

sudo concede il privilegio necessario a gestire la unit di sistema. La password resta nel terminale. Il riavvio interrompe le azioni attive e ripete warmup e apertura del microfono. Non usare il solo hash del binario per dimostrare una modifica Python caricata: controlla il nuovo processo vocale e la nuova normalizzazione nei log.

Modificare la configurazione della unit

Per un parametro del servizio si può usare un override systemd con sudo systemctl edit gpio-llm-ready.service. Esempio di contenuto, da adattare al dispositivo reale:

[Service]
Environment="GPIO_VOICE_COMMAND_TIMEOUT=15"
Environment="GPIO_WAKE_CONFIDENCE=0.90"

Dopo una modifica ai file unit, esegui sudo systemctl daemon-reload e poi il restart. daemon-reload rilegge la configurazione di systemd, non riavvia da solo l’applicazione. Un override può prevalere sull’ambiente scritto dall’installer: includi anche gli override quando fai diagnosi con systemctl cat.

Prova isolata del microfono: solo durante una finestra di manutenzione

Per aprire un secondo registratore o usare la modalità manuale, ferma prima il daemon. Questo interrompe il servizio e le azioni in corso; al termine va riavviato. Non è una procedura da eseguire mentre vuoi continuare a usare la PoC autonoma.

sudo systemctl stop gpio-llm-ready.service
cd /home/max/gpio-llm
.venv-voice/bin/python voice/stt.py --seconds 8 --save recordings/prova.wav
.venv-voice/bin/python voice/stt.py --wav recordings/prova.wav
sudo systemctl start gpio-llm-ready.service

La prima prova crea un WAV e il JSON associato; la seconda trascrive il file senza aprire il microfono. Il normale funzionamento autonomo non conserva questi file. In alternativa sh voice/run.sh avvia il percorso manuale completo, a servizio fermo.

Riprodurre l’ambiente su un altro Raspberry

Questa procedura presuppone Linux ARM64, accesso GPIO per l’utente del progetto, Rust/Cargo funzionanti e Ollama installato come servizio locale. Modelli e dipendenze vanno predisposti con Internet; l’uso ordinario successivo è locale. Non è un installer universale per qualsiasi scheda o microfono.

  1. Copia il progetto in una directory definitiva sulla scheda prima di compilare, perché alcuni percorsi vengono incorporati nel binario.
  2. Installa Python con venv/pip e arecord (ALSA), poi crea l’ambiente mostrato sotto.
  3. Identifica il microfono con arecord -l e imposta GPIO_VOICE_DEVICE se il nome differisce.
  4. Assicurati che il servizio Ollama locale abbia qwen3:0.6b disponibile.
  5. Esegui test e build, verifica la cattura e il cablaggio, poi installa la unit autonoma con l’utente del progetto.
python3 -m venv .venv-voice
.venv-voice/bin/python -m pip install -r voice/requirements.txt
mkdir -p models
curl --fail --location --output models/vosk-model-small-it-0.22.zip \
  https://alphacephei.com/vosk/models/vosk-model-small-it-0.22.zip
python3 -m zipfile -e models/vosk-model-small-it-0.22.zip models
ollama pull qwen3:0.6b
cargo test --locked
cargo build --release --locked
python3 install-autonomous-service.py --print-unit
python3 install-autonomous-service.py --install

L’ultimo comando installa e avvia il servizio di sistema e richiede sudo nel terminale. Le variabili supportate presenti quando esegui l’installer possono essere riportate nella unit; GPIO_VOICE_HOME e GPIO_VOICE_SECONDS non fanno parte di quell’elenco di persistenza dell’installer autonomo.

Perché i test sono vicini alle funzioni

Rust usa #[cfg(test)] mod tests e #[test]. Il codice dei test viene compilato nel programma di prova, non come flusso del daemon. Python usa classi unittest.TestCase e metodi test_…. I fake recognizer e le funzioni di richiesta iniettate permettono di verificare decisioni e sequenze senza aspettare audio o server reali.

assert_eq! confronta valore atteso e ottenuto; assert! verifica una condizione. Nei test Python patch sostituisce temporaneamente una dipendenza. Un fake non deve essere interpretato come dimostrazione che la dipendenza reale non possa fallire: serve a isolare una proprietà dell’applicazione.

Esempio: aggiungere un modo di dire un intervallo

Prima specifica l’interpretazione attesa e casi in cui rifiutare. Scrivi un test Python sulla trasformazione testuale, senza audio. Se aggiungi un’unità, verifica anche la scala in Rust e il validatore: una normalizzazione corretta può produrre un valore sotto il minimo. Poi prova la frase con Vosk e controlla separatamente la trascrizione, il testo normalizzato e la Action risultante.

Esempio: aggiungere un’azione

Un modello non può inventare in sicurezza un’operazione che il codice non implementa. Definisci campi RawCommand, presenza o assenza, vincoli e tipo Action; aggiorna schema e prompt, poi implementa l’esecutore con rilascio delle risorse. Aggiorna anche Numbers::constrain(): il suo match è esaustivo sulle varianti attuali e deve sapere quali numeri conservare.

In Rust un nuovo ramo enum può causare errori di compilazione nei match non esaustivi: sono indicazioni utili sui punti da aggiornare. Una nuova stringa stato in Python non dà lo stesso tipo di aiuto; per questo i test delle transizioni sono essenziali.

Esercizio di lettura

Senza eseguire nulla, segui «lampeggia LED ogni mezzo secondo» attraverso normalize_command, extract, constrain e validate. Il pin sarà None. Ora immagina che il modello proponga pin17: individua la riga che rimuove quel numero inventato e il punto che produce MissingPin.

18 / Confini della PoC

Conoscere i limiti
fa parte del know-how.

  • Il sistema non autentica la persona. ASCOLTA può essere pronunciata da un’altra persona o riprodotta da un altoparlante.
  • La comprensione resta fallibile. Il prefiltro è lessicale e l’LLM può interpretare male negazioni, frasi composte o richieste fuori dominio. La policy limita numeri e azioni rappresentabili; non prova l’intenzione umana.
  • I numeri sono protetti rispetto alla trascrizione. Errori acustici già presenti nel testo possono passare come valori validi.
  • Non è una conversazione. Se manca un parametro il programma rifiuta e chiede di ripetere una frase completa. Non mantiene un dialogo per riempire i campi.
  • Non tutte le frazioni o unità sono supportate. Per esempio «un sedicesimo di secondo» non è normalizzato; 0.0625 s sarebbe comunque sotto il minimo attuale.
  • Le azioni sono una per richiesta. Non sono implementati programmi multi-comando, conteggi di lampeggi, minuti o ore nel percorso numerico vocale.
  • Esito software e riscontro fisico sono distinti. Non esiste un sensore che controlli il LED o il carico.
  • Il tempo è governato dallo scheduler Linux. Gli sleep non costituiscono una garanzia real-time; la coda introduce attesa e la conferma vocale aggiunge circa 1.2 s nominali prima di avviare l’azione.
  • Durante elaborazione ed esito non si accodano nuove frasi vocali. L’audio viene drenato e ignorato; si ricomincia dopo il riarmo.
  • La chiusura di un client non è un arresto del backend. Un timeout non invia cancellazione e un esci non ferma il daemon.
  • La pulizia normale non copre ogni guasto fisico. SIGKILL e mancanza di alimentazione impediscono l’esecuzione dei gestori software.
  • La configurazione è locale e concreta. Il codice conserva default e messaggi di una precedente fase llama-server. Portare la PoC altrove richiede verificare endpoint, percorsi, utente, pin e dispositivo audio.
19 / Lessico del progetto

Le parole che incontrerai
nel codice e nei log.

Backend / daemon
Processo persistente che riceve richieste e possiede la logica e l’hardware. Qui è gpio-llm --daemon.
CLI / REPL
Interfaccia testuale e ciclo che legge una riga, la elabora e torna al prompt.
STT
Speech to Text: conversione del parlato in testo. Nel progetto la esegue Vosk.
LLM / inferenza
Modello linguistico e operazione che lo usa per generare una risposta, senza addestrarlo di nuovo.
Token
Unità di testo usata dal modello; non coincide necessariamente con una parola italiana.
PCM / sample rate
Campioni audio numerici e numero di campioni al secondo. Il flusso richiesto qui è mono, 16 bit, 16 kHz.
Wake word / grammatica
Parola di attivazione e vocabolario ristretto usato per riconoscerla.
Processo / thread
Un processo ha memoria propria; i suoi thread condividono memoria e possono lavorare in parallelo o alternarsi.
Pipe / file descriptor
Canale di byte fra processi e identificativo Linux di una risorsa aperta. stdin, stdout e stderr sono descrittori standard.
Socket Unix
Canale locale fra processi rappresentato da un percorso, con permessi filesystem.
Frame / newline
Un messaggio completo e il separatore di riga che ne definisce la fine nei protocolli locali.
Serde / serializzazione
Libreria Rust che converte valori tipizzati in formati come JSON e viceversa.
Option / Result
Option descrive valore presente o assente; Result descrive successo o errore. Non rappresentano la stessa cosa.
Enum / struct / impl
Alternativa fra varianti, raggruppamento di campi e blocco di metodi associati a un tipo.
Ownership / borrowing
Proprietà della risorsa e prestito controllato dell’accesso, verificati dal compilatore Rust.
Arc / Mutex
Proprietà condivisa fra thread e accesso esclusivo temporaneo ai dati condivisi.
Closure / callback
Funzione anonima che cattura contesto e funzione invocata da un componente al verificarsi di un evento.
Drop / RAII
Pulizia legata alla durata di un oggetto, usata per pin, worker e socket nei ritorni normali.
AtomicBool
Booleano leggibile e scrivibile atomicamente fra thread. Qui comunica lo stop al worker GPIO.
Policy / whitelist
Regole applicative e lista esplicita di pin ammessi. Una lista di pin non descrive il cablaggio.
GPIO / BCM / pin fisico
Uscita digitale, numero del segnale del chip e posizione sul connettore. BCM17 è il fisico11.
Semiperiodo
Durata di uno stato nel lampeggio. Due semiperiodi formano un ciclo acceso/spento completo.
systemd / unit
Gestore Linux dei servizi e file che descrive avvio, utente, ambiente, dipendenze e riavvii.
journal / PID / segnale
Archivio dei log, identificativo di processo e notifica del kernel usata anche per richiedere l’arresto.
venv / pip
Ambiente Python isolato e strumento che vi installa i pacchetti; il modello Vosk è un insieme di file separato.
Snapshot / SHA-256
Copia del codice a una data e impronta dei byte. Un hash uguale dimostra identità dei file confrontati, non che un processo abbia ricaricato Python.
